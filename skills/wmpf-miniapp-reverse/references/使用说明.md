# WMPFDebugger 使用说明（微信小程序逆向）

> 本文件是 `wmpf-miniapp-reverse` skill 的详细说明书副本。
> 工具本体在上游仓库里自带 `README.zh.md` / `FAQ.zh.md` / `EXTENSION.md` / `ADAPTATION.md`，
> 本文件只写**本机实测出来的东西**与操作细节。

## 1. 这套东西由什么组成

| 组件 | 说明 |
|---|---|
| WMPFDebugger（Node/TS） | 主程序：Frida 注入 + 私有 protobuf 调试协议 ↔ 标准 CDP 的翻译 + 两个 WebSocket 服务 |
| Frida（npm 包，17.3.2） | 注入 `WeChatAppEx.exe`；`frida_binding.node` 约 115 MB，装一次即可 |
| 微信 WMPF 运行时 | 被调试对象。本机路径 `C:\Users\y\AppData\Roaming\Tencent\xwechat\xplugin\Plugins\RadiumWMPF\<版本>\extracted\runtime\WeChatAppEx.exe` |
| 浏览器内置 DevTools | 调试前端，用 `devtools://` 打开。**不需要额外安装 Chromium** |

两个端口：

| 端口 | 作用 | 谁连谁 |
|---|---|---|
| 9421 | 调试服务（`debugPort`） | 小程序 → 本机。README 注明**不要改** |
| 62000 | CDP 代理（`cdpPort`） | 浏览器 DevTools 前端 → 本机。可改，两边参数要一致 |

## 2. 完整流程

### 首次（或重启电脑后）

```powershell
cd D:\AI_python\reverse\vmpfdebugger
.\start-debugger.ps1        # 窗口保持开着
```

看到这四行才算成功：

```
[server] debug server running on ws://localhost:9421
[server] debug server waiting for miniapp to connect...
[server] proxy server running on ws://localhost:62000
[frida] script loaded, WMPF version: 16467, pid: 2788
[frida] you can now open any miniapps
```

然后在微信里**打开（或关掉重开）**目标小程序。重新打开后调试器窗口应出现：

```
[miniapp] miniapp client connected
```

最后另开一个 pwsh 窗口：

```powershell
.\open-devtools.ps1
# 浏览器打开后：Ctrl+L → Ctrl+V → 回车
```

出现 `[cdp] CDP client connected` 即全部就绪，DevTools 里就能看到小程序了。

### 为什么必须"重开小程序"

Frida 是在小程序**加载时**patch 运行时的。调试器启动前就已经打开的小程序不会连上 9421，
必须在注入之后重新加载一次。

### 会话中反复出现的 connect / disconnect

小程序每个页面/JS 上下文重建时会重连一次，日志里出现多次
`miniapp client connected` / `disconnected` 是正常的；只要最终保持 `connected` 即可。

## 3. CLI 参数

`start-debugger.ps1` 透传给 `src/index.ts`：

| 参数 | 默认 | 用途 |
|---|---|---|
| `-CdpPort` | 62000 | CDP 代理端口（浏览器链接里的端口） |
| `-DebugPort` | 9421 | 小程序回连端口（别改） |
| `-DebugMain` | 关 | 打印小程序侧 CDP 消息流（排障利器） |
| `-DebugFrida` | 关 | 打印 Frida 脚本消息 |
| `-AutoDetect` | 关 | 自动探测 hook 偏移（Windows x64，beta；版本未适配时用） |
| `-Root` | `D:\AI_python\reverse\vmpfdebugger` | 工具目录，可从 skill 目录直接调用 |

`open-devtools.ps1`：`-CdpPort`、`-Browser`（指定浏览器 exe）、`-NoBrowser`（只复制链接）、
`-AutoPaste`（实验性自动粘贴，焦点可能被抢走）。

## 4. 日志解读（排障时的判断依据）

| 日志 | 含义 / 下一步 |
|---|---|
| `[frida] script loaded, WMPF version: 16467, pid: 2788` | 注入成功。pid 是 WMPF **主进程**（不是随便一个渲染进程） |
| `[frida] version config not found: XXXXX` | 该 WMPF 版本没适配 → 见第 7 节 |
| `[frida] auto-detect failed: ...` | `-AutoDetect` 探测失败，改用别的办法 |
| `[frida] WeChatAppEx.exe process not found` | 微信没运行，或权限不足 |
| `[miniapp] miniapp client connected` | 小程序已连上（**没这句就别开浏览器**） |
| `[cdp] CDP client connected` | 浏览器前端已连上 |
| 完全没有上述任何一行 | 顺序错了 / 小程序没重开 / 全局代理捣乱 |

想看 CDP 消息流（例如确认浏览器发了什么、小程序回了什么）：加 `-DebugMain`，
日志会打印十六进制原文与解码后的对象。

## 5. DevTools 里能做什么

| 面板 | 情况 |
|---|---|
| Sources | 小程序 JS 全在这里；`{}` 按钮格式化压缩代码；行号断点、条件断点 |
| Console | 在小程序运行时求值；断点命中后可访问作用域变量 |
| Network | 小程序发起的请求（WebView 内的看不到） |
| Debugger | 调用栈、XHR/fetch 断点、事件监听断点、异常暂停 |
| Elements | **基本为空** —— 小程序不是 DOM 环境，别在这里找元素 |

### 常用手法

1. **找接口与参数**：Network → 目标请求 → 看 Payload / Initiator → 在 Sources 对应位置下断点 →
   复现操作 → 在 Call Stack 里逐层读参数来源。
2. **抓签名 / 加密**：Sources 全局搜索 `sign` / `encrypt` / `md5` / `sha` / `timestamp` / `nonce` /
   `aes` / `sm2` 等 → 断点 → 单步进加密函数。
3. **运行时取值**：Console 直接算；或断点命中后在 Console 读当前作用域变量。
4. **Hook 目标函数**（Console 里执行）：
   ```js
   const _f = SomeObj.target;
   SomeObj.target = function (...a) { console.log('args', a); return _f.apply(this, a); };
   ```
5. **抓返回数据**：Network 面板右键请求 → Copy response；或在断点处取局部变量。

## 6. 链路排障

```powershell
node $DSH_HOME\skills\wmpf-miniapp-reverse\scripts\probe-cdp.js
```

它自己当第二个 CDP 客户端连 62000，发 `Runtime.enable` 等命令，**有响应就说明
「代理 ↔ 小程序」这段是通的**（本机实测可收到 700+ 条消息与持续 `Page.screencastFrame` 画面帧）。
这能把问题切成两半：

| probe 结果 | 结论 |
|---|---|
| 有响应，但浏览器空白 | 前端问题 → DevTools 页面按 `F5` 刷新（前端初始化命令丢失） |
| 无响应 | 小程序没连上 → 看调试器日志有没有 `miniapp client connected`；没有就重开小程序 |
| 连不上端口 | 调试器没跑 / 端口不符 / 上次进程没清干净 |

## 7. WMPF 版本与适配

- 查版本：任务管理器 → `WeChatAppEx` → 右键「打开文件所在的位置」，
  `RadiumWMPF` 与 `extracted` 之间的数字即版本。
- 工具按版本读 `frida\config\win32\addresses.<版本>.json`（内含
  `LoadStartHookOffset` / `CDPFilterHookOffset` / `SceneOffsets`）。
- 版本未适配时的三条路：
  1. `-AutoDetect`（Windows x64，beta，自动找偏移）；
  2. 等上游适配（提 issue，需要作者有对应版本 binary）；
  3. 照上游 `ADAPTATION.md` 自己找偏移量（用 IDA/调试器分析 `WeChatAppEx.exe`）。
- 微信 4.x 更新方式：官网 `pc.weixin.qq.com` 下最新版安装包，WMPF 随包更新。
  微信 4.x 以下：搜索框输入 `:showcmdwnd`（不要回车触发搜索）→
  `/plugin set_grayvalue=202&check_update_force` → 重启微信。
- 本机状态：微信 4.x，WMPF **16467**，仓库自带该版本配置，实测通过。

## 8. 上游 FAQ 要点（与本机实测一致的）

- 安装**不要用 npm**，用 yarn，且不要删 `yarn.lock`（frida API 变动快，需要锁版本）。
- `yarn install` 卡在 `Building fresh packages`：frida 预编译二进制下载慢，挂代理重试。
- `Cannot read properties of undefined (reading 'parameters')`：frida 版本不对（用 yarn 重装）或权限不足（提权 node）。
- 小程序闪退：① 全局代理（yakit 等）导致 WebSocket 帧错误；② 顺序错误；③ 版本不匹配。
- 小程序无限加载：先关调试器 → 打开小程序正常加载一次 → 再按三步重来。
- 启动成功但 Network 无流量：小程序内嵌 WebView 是独立进程，需另走上游 `EXTENSION.md`。
- 公众号 / 微信内置浏览器：上游 `EXTENSION.md`，仅有基础调试能力。

## 9. 合规与许可

- 只调试**你有权调试**的小程序（自己的、客户授权明确覆盖的）。第三方目标先走
  `reverse-skill-router` 的 case-init 授权门禁。
- 上游 WMPFDebugger 为 **GPLv2**：改动或分发衍生版本必须保留版权与贡献者署名。
- `src\third-party\` 下的协议实现提取自微信开发者工具，版权属腾讯控股有限公司。
- 工具本身不读取、不保存任何微信凭据；登录态始终由本机微信进程持有。
- 本机不安装额外的 Chromium：调试前端复用系统浏览器（本机 Edge 143 已验证）。
