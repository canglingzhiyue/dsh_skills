# 评审协议（拿不准就评审）—— v1，2026-11-01 用户定

> 用户指令原文要点：**后面遇到拿不准的，派 subagent 一起沟通**，按「是否有漏洞 / 是否会冲突 / 是否最优解 /
> 就算当前方案可行，后期出现新证据是否容易修正 / 以及其他没想到的方向」比较校验，**确认出最佳方案后再跑**，
> 后续进程一律照此执行。

## 一、什么时候必须评审（触发条件，任一命中即触发）

1. 有 **≥2 个可行方案**，且手上没有实测数据能直接决出胜负；
2. 改动会**影响 ≥10 条规则**、或跨 ≥2 个主题、或改到根 `SKILL.md` / schema / 闸门脚本；
3. 涉及**不可逆或高成本**动作（批量改稿、重跑全量、联网抓取、落盘到 `~/.dsh/skills`、推账本）；
4. 我**自己心里没底**——这条优先于前三条，别硬撑；
5. 用户明确要求评。

**不评审**：单条规则的措辞、显然是 bug 的修复、有唯一正确答案的事实问题。

## 二、评审维度（六维，前五维是用户指定，第六维是补充）

| 维度 | 问的问题 | 打分 |
|---|---|---|
| **漏洞** Voids | 正确性有没有洞？边界/失败模式是什么？会不会悄悄产出错数据？ | 1–5 |
| **冲突** Conflicts | 与 `plan.md` 既定决策、既有 skills、前序产物、`dev-hygiene` 红线是否打架？ | 1–5 |
| **最优解** Optimality | 在「省上下文 + 省维护」的约束下，有没有更省的做法？ | 1–5 |
| **可修正性** Reversibility | **就算现在可行**，将来出现新证据时改起来要动几个文件、要不要重跑、会不会破回归基线？ | 1–5 |
| **盲区** Blind spots | 还有哪些没人想到的角度？（用户第 4 点明确要求补充） | 1–5 |
| **预算** Budget | 是否守住根 ≤6k / 主题 ≤12k / 索引 ≤8k / 全树 ≤250KB / 单次加载 ≤30k 字符 | 1–5 |

**判定规则**
- 任一维度 **≤2 分 → 该方案否决**，不许"整体还行"糊过去；
- 推荐方案必须写清 **「最坏情况下错在哪 + 多久能被发现」**；
- 评审方必须给出**至少一条反对意见或隐性风险**，禁止只写优点（防走过场）；
- 并列最优时，**选可修正性更高的那个**（这条是本协议的核心取向：宁可现在笨一点，也不要将来改不动）。

## 三、输出格式（固定，便于以后逐次对比）

```markdown
# 评审：<主题> — <日期>

## 待决问题
1. <问题>：<候选 A> vs <候选 B> vs <现状>

## 六维评分
| 候选 | 漏洞 | 冲突 | 最优解 | 可修正 | 盲区 | 预算 | 合计 | 结论 |
|---|---|---|---|---|---|---|---|---|

## 逐条理由（每个候选 ≤3 句）

## 盲区清单（我没被问到但该考虑的）

## 推荐方案 + 落地清单
- 改哪个文件、怎么改、影响面、回滚方式

## 最坏情况
- 错在哪：
- 多久能发现：
- 发现后怎么退：
```

## 四、评审记录落在哪

- 单次评审全文：`output/drafts/review-<日期>-<主题>.md`
- 结论摘要 + 是否采纳 + 落地结果：追加到 `journal.md` 的「评审记录」段，**带方案 ID**，便于将来翻案时溯源。
- 被否决的方案**不删除**，留在评审文件里——它是"以后新证据可能翻案"的存档。

## 五、评审之后怎么跑

1. 采纳 → 按落地清单改 → 重跑闸门（`check_budget` / `check_links` / `run_cases`）→ journal 记一行结果；
2. 否决全部候选 → 回到问题定义，**不要**在否决的方案上打补丁；
3. 评审方给的盲区里如果有值得做的 → 单独建一条待办，不混进当前改动（防止范围蔓延）。
