#### jingtai-005 文案搜不到就改走 arsc 资源 ID 反查

- 失效条件：目标上资源混淆/资源 ID 重排（AndResGuard 类）后，资源名与 ID 都不再稳定对应文案
- 证据：strong ｜ 6源(52pj6) ｜ 2020–2026 ｜ 命中16

#### jingtai-006 字符串搜不到先分四种根因再动手
- 症状：关键字符串搜不到；以为字符串被加密了

- 动作：按单 dex→全 dex→arsc→看偏移周期→倒序/十六进制各试一次，再下「被加密」结论。
- 无效则：四种都排除 → 去初始化函数找解密循环，或转动态取内存明文。
- 失效条件：字符串运行时才解密并在用后 free 时，静态搜任何形态都不会命中
- 证据：strong ｜ 4源(52pj3/kanxue1) ｜ 2021–2026 ｜ 命中89

## 阶段：校验

<a id="jingtai-012"></a>
#### jingtai-012 认出 memcmp 与 abort 这类校验原语
- 症状：校验过不去；改返回值也没用　报错：`Fatal signal 6 (SIGABRT)`
- 判断：出现 memcmp → 先读长度参数，长度就是「比到第几字节」；出现 abort() → 硬校验，不走返回值判断，改跳转与改返回都无效
- 动作：memcmp 长度参数改 0（或一两字节前缀更隐蔽）；abort() 直接 NOP 调用点。
- 无效则：常量时间比较/自实现逐字节比对 → 改期望值那一侧，别改比较函数。
- 失效条件：校验被内联成逐字节比较或用哈希整体比对时，找不到单个 memcmp 调用点
- 证据：weak ｜ 3源(52pj3) ｜ 2020–2021 ｜ 命中6
- 锚点：1350687,1290361,1407723

## 阶段：补丁

<a id="jingtai-015"></a>
#### jingtai-015 补丁优先改返回值而不是改跳转
- 症状：不知道该改哪一处；改了跳转就崩
- 判断：授权/校验类函数大多只被调用方检查返回值 → 1 到 8 字节的返回桩就够，改动面最小；改跳转要算分支方向、还可能跳过跳转前的赋值，崩的概率高得多
- 动作：按架构写返回桩：ARM32 E3A00000+1E FF 2F E1 / Thumb 0020+70 47 / ARM64 W0,#imm+C0 03 5F D6；先确认返回值真是 bool。
- 无效则：返回结构体或必须保留副作用 → 改内部那次比较的期望值，别整体短路。
- 失效条件：目标用返回值做后续计算（数值而非开关）时，返回常量会让下游结算/评分逻辑崩掉
- 证据：strong ｜ 5源(52pj5) ｜ 2019–2025 ｜ 命中8
- 锚点：1013685,1024836,1328122,2079083,941865

<a id="jingtai-016"></a>
#### jingtai-016 返回桩必须等长且带上返回指令
- 症状：patch 后直接闪退；改了返回 0 还是原来的值　报错：`Fatal signal 11 (SIGSEGV), code 1 (SEGV_MAPERR)`
- 判断：只写 MOV R0,#0 不回跳 → 函数继续执行原指令把返回值覆盖掉；替换指令比原指令长 → 把后面的 BX LR 一并覆盖，函数返回地址错乱
- 动作：Thumb 2 字节定长，多出字节补 00，结尾必须 BX LR/RET；ARM/Thumb 看地址最低位。
- 无效则：原指令本身就比返回桩短 → 找一段长 nop 当跳板，别硬塞。
- 失效条件：函数入口被编译成 Thumb-2 宽指令或存在多条返回路径时，替换入口两条指令不足以覆盖全部出口
- 证据：strong ｜ 4源(52pj4) ｜ 2017–2019 ｜ 命中33
- 锚点：1024836,849354,1027341,657923

<a id="jingtai-017"></a>
#### jingtai-017 smali 分支先核方向再决定反转
- 症状：改了 if 还是不生效；改完流程走岔了
- 判断：smali 的 if-* 是「条件成立就跳」，与 Java 的 if 方向相反；if-eqz=等零则跳、if-nez=不等零则跳，反编译注释经常把方向写反
- 动作：看 label 落在哪侧：label 是要绕开的失败逻辑 → 反转 if-eqz↔if-nez；跳转多余 → goto；别删整段。
- 无效则：两处分支汇到同一 label → 改跳转无意义，改汇合前给结果寄存器的常量赋值。
- 失效条件：目标把判定写成三态链（永久/普通/非会员）时，反转最外层只改提示不改功能
- 证据：strong ｜ 5源(52pj5) ｜ 2019–2020 ｜ 命中114
- 锚点：1039699,1214161,1245052,1328309,1192009

<a id="jingtai-018"></a>
#### jingtai-018 改判断前插常量，别删调用
- 症状：删了判断就崩；不知道改产生方还是消费方
- 判断：move-result 拿的是上一次调用的返回值，紧跟的 if-*z 就在判它 → 该改「谁给这个寄存器赋值」而不是删跳转；命中多处时只看消费方会漏掉别的调用点
- 动作：在 if-*z 前插 const/4 vX,0x1（或 0x0），保留原调用；优先改判定方法本体覆盖所有调用点。
- 无效则：判定是 long/double 比较（cmp-long/cmpl-double）→ 不能用 const/4，按位宽补 const-wide。
- 失效条件：判定由服务端返回值驱动时，改本地常量只改变显示，功能仍被服务端拒绝
- 证据：strong ｜ 4源(52pj4) ｜ 2020–2020 ｜ 命中18
- 锚点：1134752,1250697,1287250,1326601

<a id="jingtai-019"></a>
#### jingtai-019 改 dex 必按 file_size→signature→checksum 修
- 症状：改完 dex 装不上或校验失败；重打包后提示损坏
- 判断：dex 头 0x20=file_size、0x0C=SHA-1（从 0x20 起算）、0x08=Adler-32（从 0x0C 起算）；后一步覆盖前一步的范围，顺序错就互相污染
- 动作：按 file_size → signature → checksum 顺序重算并回搜确认；Manifest 与 dex 的版本号要对齐。
- 无效则：改的是 oat/vdex 层 → oat 是索引、vdex 是数据，dex_file_offset 相对 vdex 的 dex 区。
- 失效条件：目标用自己的解析器读 dex 并额外校验头部保留字段时，只修这三处仍会被判非法
- 证据：strong ｜ 3源(52pj3/kanxue0) ｜ 2019–2021 ｜ 命中17
- 锚点：1057245,1494281,1408504

## 阶段：验证

<a id="jingtai-004"></a>
#### jingtai-004 改完没变化先验证改的东西有没有跑
- 症状：装得上、跑起来、就是没变化；改完毫无效果也不报错
- 判断：包结构正常但代码全灰、方法体全空 → 真 dex 是运行时释放的，磁盘那份根本没被加载；此时「改得对不对」不是问题，「改的东西没跑」才是
- 动作：先确认加固形态（assets 大文件、方法体 nop），再转脱壳或 dump 内存 dex。
- 无效则：代码可读仍无变化 → 查多 dex、查第二条计费/校验路径。
- 失效条件：壳改成运行时从内存回填方法体、磁盘 dex 保持原始明文时，静态改动同样无效
- 证据：weak ｜ 3源(52pj3) ｜ 2021–2024 ｜ 命中3
- 锚点：1408504,1494281,1918003

<a id="jingtai-026"></a>
#### jingtai-026 签名算法要用抓包值逐字节验完才收工
- 症状：算法算出来了但服务端不收；签名差几位
- 判断：只算出 MD5 不算验证 → 必须与抓包提交值逐字节一致；差一个字符先查字段顺序、拼接符与 URL 编码，再查 sign 本身是否被排除在参与字段之外
- 动作：核对三件套：参与字段（sign 是否排除）、顺序、拼接符与盐；最后改参重算→服务端接受的闭环。
- 无效则：三项都对仍不一致 → hook 签名函数直接看实参，与静态拼出的原文互证。
- 失效条件：签名含时间片/nonce 或服务端加了下发校验时，静态拼出的原文只能对当次请求成立
- 证据：strong ｜ 4源(52pj4) ｜ 2016–2020 ｜ 命中35
- 锚点：1311533,539718,1140773,1199629
