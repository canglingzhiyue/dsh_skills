## 阶段：侦察

<a id="hook-001"></a>
#### hook-001 下钩前先做重签与断网三对照
- 症状：改完没生效；不知该改哪一层
- 判断：只重签就闪退 → 有签名校验；卡屏不崩 → native 主动阻塞；断网仍解锁 → 本地可改；联网才解锁 → 服务端签发，客户端无解。
- 动作：跑原包 / 仅重签 / iptables DROP 三对照，结论写进 scope 再选层。
- 无效则：三条都像校验 → 从崩溃栈的 so 名与 Java_ 前缀反推层级。
- 失效条件：校验域名与业务同域时，断网只能判本地/远程，判不出具体校验层。
- 证据：strong ｜ 4源(52pj4) ｜ 2019–2026 ｜ 命中4
- 锚点：1061722,1123332,2110849,1029891

<a id="hook-002"></a>
#### hook-002 有壳先脱壳再看代码
- 症状：jadx 里只有壳类；hook 报找不到类　报错：`java.lang.ClassNotFoundException`
- 判断：Manifest 的 android:name 是 com.stub.* / StubApp / TxAppEntry 且业务包名为空 → 真 dex 运行时才释放。
- 动作：按保护粒度分流（整文件 dump / 单函数 dump+还原）后再 jadx；长度取 dex 头 0x20 的 file_size。
- 无效则：dump 后函数体为空 → 脱不全，覆盖所有进程再 dump。
- 失效条件：目标用 InMemoryDexClassLoader 局部加载 dex 时整包 dump 拿不到，必须在加载点 hook。
- 证据：weak＋缺口 ｜ 4源(kanxue4) ｜ 2023–2026 ｜ 命中6
- 锚点：279381,279403,280082,292792

<a id="hook-003"></a>
#### hook-003 启动期只跑一次的逻辑必须 spawn
- 症状：hook 挂上了没打印；attach 后拦不到
- 判断：逻辑落在 Application 构造、attachBaseContext、static 块或 .init_array → 只在启动瞬间执行，attach 时已跑完，所以「能挂上但抓不到」。
- 动作：用 frida -f 起进程，更早时机加 --startup-command；线程名类特征只存在一瞬间，晚期 attach 必漏。
- 无效则：spawn 仍秒退 → 换常驻框架或去特征版本，按退出方式定位。
- 失效条件：检测的是「是否被注入」而非某函数是否被调时，更早注入只让检测更快命中。
- 证据：strong ｜ 3源(kanxue3) ｜ 2024–2025 ｜ 命中3
- 锚点：281761,286006,284601

<a id="hook-004"></a>
#### hook-004 按导出表形态分流静态与动态注册
- 症状：IDA 搜不到目标函数；native 声明找不到实现
- 判断：导出表有 Java_包名_类_方法 → 静态注册，直接 F5；只有 JNI_OnLoad 没有 Java_ 前缀 → 动态注册，函数名与 Java 名无关。
- 动作：先看导出表与 JNI_OnLoad 各一眼定性，再决定静态跳转还是读注册表。
- 无效则：两者都没有 → 怀疑注册被下沉，改读 ArtMethod 入口槽位。
- 失效条件：壳用 ShadowHook/Dobby 接管注册路径时 JNI_OnLoad 里看不到 RegisterNatives，得在可疑偏移看参数是否出现 ClassLinker。
- 证据：strong ｜ 3源(52pj0/kanxue3) ｜ 2025–2025 ｜ 命中141
- 锚点：285362,285550,287969

<a id="hook-005"></a>
#### hook-005 别在已停更的 Xposed 派生框架上搭方案
- 症状：照老教程装的框架不生效；模块列表显示未启用
- 判断：原版 Xposed 2017 停更且只到 Android 8.x，EdXposed 已停更，Riru 被 Magisk v24 的 Zygisk 取代 → 老教程的框架在新设备起不来。
- 动作：现役：Java 常驻 → Magisk(Zygisk)+LSPosed；要快 → Frida；免 root → LSPatch。只复用 API 写法，不复用安装链。
- 无效则：换新框架仍被检测 → 转框架检测面分流。
- 失效条件：目标只跑 Android 8 以下或 ROM 内置旧框架时旧路仍可用；LSPosed 开源版不支持 Android 15+。
- 证据：weak ｜ 4源(52pj4) ｜ 2022–2023 ｜ 命中20
- 锚点：1694093,1718014,1626920,1748081

## 阶段：定位

<a id="hook-006"></a>
#### hook-006 真实 ClassLoader 只在运行时取
- 症状：hook 不生效但类已加载；findClass 报找不到类　报错：`java.lang.ClassNotFoundException`
- 判断：壳在 attachBaseContext 后才装真 dex → 框架 loader 解析不到业务类。
- 动作：从 Manifest 的 android:name 找壳入口，在 attachBaseContext 的 after 钩子里取 context.getClassLoader()。
- 无效则：运行时还会换 loader（热修复）→ 枚举 ClassLoader 链表递归取。
- 失效条件：目标拿 ClassLoader 数量当反注入特征时，拿整条链表的 loader 去 hook 即暴露面。
- 证据：weak＋缺口 ｜ 4源(52pj1/kanxue3) ｜ 2021–2025 ｜ 命中33
- 锚点：279381,279440,1364632,289567

<a id="hook-007"></a>
#### hook-007 动态注册就 hook RegisterNatives 拿全表
- 症状：native 方法找不到实现；不知加密在哪个 so
- 判断：映射只存在于 RegisterNatives 入参，那里同时有类名/方法名/签名/函数指针；fnPtr 减模块基址即 IDA 偏移。
- 动作：筛 libart.so 里含 art+JNI+RegisterNatives 且不含 CheckJNI 的符号，按 3×pointerSize 解表项。
- 无效则：打印为空 → 补 CheckJNI 过滤；Module 名不可信，用 enumerateModules 按地址重算。
- 失效条件：加固绕过 JNI 入口直接往 ArtMethod 写入口点时，RegisterNatives 与 dlsym 全空。
- 证据：weak＋缺口 ｜ 3源(52pj0/kanxue3) ｜ 2024–2025 ｜ 命中71
- 锚点：286004,282553,287899

<a id="hook-008"></a>
#### hook-008 RegisterNatives 抓不到就改读 ArtMethod
- 症状：RegisterNatives 与 dlsym 全空；注册在 attach 前完成
- 判断：注册下沉到 ART 内部 ArtMethod::RegisterNative 时不经 JNI 公开入口 → 两个常规点都空，但地址最终写进 ArtMethod，读结果比抓动作便宜。
- 动作：拿到 ArtMethod 后读入口/数据槽位取已解密地址；偏移按指针宽度算，用已知 JNI 导出符号校准。
- 无效则：读到的仍是跳板地址 → 该方法是 VMP，转 unidbg 或指令级 trace。
- 失效条件：目标改用类替换（整体换 ArtMethod）时原槽位不再被写，需在替换链路上取。
- 证据：weak＋缺口 ｜ 3源(kanxue3) ｜ 2024–2024 ｜ 命中19
- 锚点：281427,282707,285135　依据在图中，未复核

<a id="hook-009"></a>
#### hook-009 地址一律 base+offset，换版本按键名重解
- 症状：换版本 hook 全失效；别的机型就崩
- 判断：写死的是函数序言字节或某次 build 的绝对偏移 → 编译器版本、优化等级、linker 一变就废，是结构性原因不是运气。
- 动作：常量区只存（模块名, 符号名/特征串），运行时用 findBaseAddress + enumerateSymbols 算地址，记「版本+类名」配对。
- 无效则：符号被自实现 linker 抽走 → 按节区自解符号表（base + st_value − (p_paddr − p_offset)）。
- 失效条件：目标每次启动重算结构体地址时静态地址方案整体退化，只能改判定输入或改客户端代码。
- 证据：weak＋缺口 ｜ 3源(kanxue3) ｜ 2024–2026 ｜ 命中9
- 锚点：281427,287899,290221

<a id="hook-010"></a>
#### hook-010 dlopen 无输出就换 android_dlopen_ext
- 症状：hook dlopen 一点输出没有；so 加载时机抓不到
- 判断：高版本加载实际走 android_dlopen_ext，aarch64 上它只是跳板，真正干活的是 do_dlopen → 只挂 dlopen 就落在没人走的路径上。
- 动作：先挂 android_dlopen_ext；更内层用 B 指令偏移从 __loader_dlopen 追到 do_dlopen；或轮询导出非空再上钩。
- 无效则：两点都没命中 → 可能自实现加载器，转 .init_array 与匿名段观测。
- 失效条件：加固自带 so 加载器、完全不经过 linker 公开入口时 dlopen 族全部失效。
- 证据：strong ｜ 3源(52pj1/kanxue2) ｜ 2020–2025 ｜ 命中37
- 锚点：1226153,284570,288558

<a id="hook-011"></a>
#### hook-011 先借现成工具抓栈再回 jadx 精准搜
- 症状：手写 hook 模板太慢；类太多不知从哪下手
- 判断：界面提示必过 Toast/setText/Dialog.show/Log 这些落地调用，在其上打栈即得「按钮→判定→弹窗」链路；该栈工具即能采到，手写模板等于重造。
- 动作：在落地调用上采栈，抄下入口/判定/出口三段类名，回 jadx 只搜这几个；确认复用才落成脚本。
- 无效则：栈里没有业务帧（native 弹窗）→ 换 syscall 层打调用方模块名+偏移。
- 失效条件：目标对注入面做检测（框架特征、loader 计数）时现成工具本身是暴露点，须自编译去特征版。
- 证据：strong ｜ 4源(52pj1/kanxue3) ｜ 2023–2026 ｜ 命中53
- 锚点：1763152,291308,293133,280758

<a id="hook-012"></a>
#### hook-012 找不到检测码就 hook 系统调用打调用方
- 症状：检测代码找不到；静态搜不到 kill/ptrace
- 判断：检测被内联成直接 svc 或多层 wrapper → 符号层看不到；但系统调用必过 svc 或内核侧，调用方栈里一定留着「模块名+偏移」。
- 动作：在 syscall 层（Stalker / ptrace / perf_event）打印调用方模块与偏移，回 IDA 定位；arm64 先核对 x8/x0 调用号。
- 无效则：静态扫 svc 代价高 → 改 seccomp 从内核侧截获，与指令位置解耦。
- 失效条件：目标扫 perf_event 参数或 TracerPid 时观测层本身会被发现，须先解决反调试。
- 证据：strong ｜ 3源(52pj0/kanxue3) ｜ 2024–2024 ｜ 命中59
- 锚点：281030,281707,283860

<a id="hook-013"></a>
#### hook-013 Binder 全量拦截走 ioctl 收口
- 症状：AIDL 代理拦不到；私有服务 hook 不到
- 判断：Sensor/Camera/Audio 只有 native 实现、不走 Java 接口 → 上层怎么调都收口到 ioctl(BINDER_WRITE_READ)，hook transact 只拦一侧。
- 动作：hook ioctl 先判 cmd == BINDER_WRITE_READ 再解 BC_/BR_ 与事务结构，非该命令原样放行保性能。
- 无效则：用户态 hook 太显眼 → seccomp-notify 内核侧粗过滤，精确匹配放用户态。
- 失效条件：目标改用 socketpair、共享内存或私有驱动通信时 ioctl 不再是唯一收口。
- 证据：strong ｜ 4源(52pj0/kanxue4) ｜ 2023–2026 ｜ 命中28
- 锚点：279725,281510,289758,291098

<a id="hook-014"></a>
#### hook-014 静态 XREF 连不上就上调试器看间接调用
- 症状：IDA 的 XREF 全是空；函数地址藏在参数里
- 判断：真实目标被 wrapper 打包进参数/寄存器或走导入表间接调用 → 静态连不上不代表没调用，调试器里看 call qword ptr [reg] 即可拿落点。
- 动作：可疑调用点下断读寄存器/栈里的目标地址再回静态定位；噪声大用条件断点按进程过滤。
- 无效则：间接调用极密集 → 导入导出定位 + 条件断点，或改调用栈采样。
- 失效条件：关键路径搬进解释器或 VM（脚本引擎、打包运行时）时该层只见 VM 循环，跳转语义不在这里。
- 证据：weak＋缺口 ｜ 3源(kanxue3) ｜ 2023–2023 ｜ 命中9
- 锚点：279502,282695,282885

## 阶段：校验

<a id="hook-019"></a>
#### hook-019 每处 kill/crc/ptrace 都要看交叉引用
- 症状：当时能用后来随机退出；换版本又要重改
- 判断：一个 so 里通常不止一处校验，壳还会把同一段检测复制到多个区段 → 只改一处是定时炸弹；应按调用点而非按函数确认。
- 动作：对 kill/exit/crc/ptrace 全部看 XREF 并按模块名过滤逐点确认，每进一次壳的 so 都重新确认。
- 无效则：调用点太多 → 改判据源头（让检测读到的值本身干净），而不是逐点置零。
- 失效条件：检测改到内核态或 eBPF 观测时用户态 XREF 里根本没有这些调用点。
- 证据：strong ｜ 3源(52pj2/kanxue1) ｜ 2019–2020 ｜ 命中195
- 锚点：280562,1103857,1030847

<a id="hook-020"></a>
#### hook-020 去特征清单不够，按退出方式逐层收敛
- 症状：已去特征仍被检测退出；清完常见特征还是被杀
- 判断：命中的可能是清单外的冷门特征，甚至运行时拼接出来的串（源码与二进制都搜不到整串）→ 判据不在清单里，加清单无用。
- 动作：按「退出方式分类 → 扫调用/比较点 → 堆栈频次 → 单函数 Stalker」四步收敛，用已知分支地址去 trace 里搜命中点。
- 无效则：收敛后仍无落点 → 判据可能在协议层或行为层，转行为观测。
- 失效条件：检测方改用内存一致性校验（比对文件与内存字节）时任何内存改写都无效。
- 证据：strong ｜ 4源(kanxue4) ｜ 2024–2026 ｜ 命中5
- 锚点：281761,282555,291309,284941

<a id="hook-021"></a>
#### hook-021 框架本身已是检测面，先判再选注入方式
- 症状：装框架就闪退；停用模块仍然打不开
- 判断：Java 层 hook 把方法改成 native 指向自身处理函数，注入还需额外造 ClassLoader → 痕迹藏不住；SELinux context 与 native.bridge 也点名框架。
- 动作：先判检测落在哪一面（Java hook 痕迹 / loader 数量 / SELinux context / native.bridge），再选去特征编译、欺骗返回值或不走框架。
- 无效则：只停用模块就恢复正常 → 检测针对模块而非框架，收窄作用域比重装快。
- 失效条件：检测方只查注入行为而不查常驻框架时，常驻框架反而是最低成本路线，前提反了。
- 证据：weak＋缺口 ｜ 4源(kanxue4) ｜ 2024–2025 ｜ 命中12
- 锚点：289567,291750,285106,280869

## 阶段：补丁

<a id="hook-015"></a>
#### hook-015 重载方法一律写全 overload 签名
- 症状：hook 报重载歧义；只在一部分场景生效　报错：`has more than one overload`；`argument types could not be found`
- 判断：混淆后同名重载极多，直接赋值定位不到唯一目标 → 框架无法替你选，只能按签名选；报错本身会列出候选签名。
- 动作：先不写 overload 直接赋值，从报错抄候选签名再逐条挂；类型写全限定名（内部类用 $），无参用空 overload()，构造用 $init。
- 无效则：所有重载都要覆盖 → 一对多全挂，或改挂最终落地那一次调用。
- 失效条件：目标是 native 或 VMP 方法时不存在 Java 重载概念，改按 so 偏移与注册表定位。
- 证据：strong ｜ 4源(52pj4) ｜ 2019–2024 ｜ 命中26
- 锚点：1069255,1097737,1888018,1428662

<a id="hook-016"></a>
#### hook-016 返回值用 replace，C 侧入参用指针写
- 症状：改了返回值没效果；参数赋数值目标没变化
- 判断：返回值是框架托管句柄，直接赋值只改本地变量；C 侧参数是指针，给 JS 数值不落到目标内存 → 「写了没用」都是类型不匹配。
- 动作：返回用 retval.replace(值)；C 侧入参用 ptr(值) 或直接写寄存器；onEnter 先把入参存到 this，onLeave 再用。
- 无效则：要改结构体字段 → 读指针加偏移后写，偏移按指针宽度算。
- 失效条件：目标拿到返回值后立刻二次校验时单点 replace 会被判不一致，须同时改校验输入。
- 证据：strong ｜ 4源(52pj0/kanxue4) ｜ 2024–2025 ｜ 命中17
- 锚点：279761,280812,282013,286004

<a id="hook-017"></a>
#### hook-017 要调原函数就先取句柄再 call
- 症状：hook 后卡死或栈溢出；一上钩就崩　报错：`StackOverflowError`
- 判断：在 implementation 内再用 this.方法名() 会重新进入自己的钩子 → 无限递归；框架不区分原始方法和被替换后的方法。
- 动作：进 implementation 前把原方法句柄存成变量（按 overload 取），需要时 orig.call(this, ...)；native 侧先恢复现场再调。
- 无效则：原函数只一条查表赋值 → 直接照抄实现写进钩子，比调原函数便宜。
- 失效条件：目标是带副作用的单例初始化方法时重复调用会破坏状态，此时只能观测不能转发。
- 证据：strong ｜ 3源(52pj3) ｜ 2019–2026 ｜ 命中9
- 锚点：1105016,2088570,1048786

<a id="hook-018"></a>
#### hook-018 改数据源方法而不是判定结果
- 症状：改一处只部分生效；值对了界面还不对
- 判断：判定方法被多处读取、还可能被 native 再判一次 → 改结果只覆盖一条路径；返回用户对象/配置的数据源方法被所有读取点共用。
- 动作：在数据源方法的返回处回填字段（先全字段打印、与界面显示比对确认链路），一次改完所有读取点。
- 无效则：字段语义不明 → 先只读打印全部字段，改一个看界面变化再批量改。
- 失效条件：关键资源由服务端按条件下发、本地只是显示壳时，改数据源只能改显示不能解锁内容。
- 证据：strong ｜ 4源(kanxue4) ｜ 2023–2024 ｜ 命中3
- 锚点：279381,280076,281427,282429

#### hook-022 算法必须用真实抓包参数复算才算验证
- 症状：自己算的和抓包不一致；算法看着对但请求失败
- 判断：把真实参数代回还原出的算法、结果与线上密文逐字一致，才证明拿到了完整输入集合；只在自己构造的样例上跑通，漏掉的盐和时间戳全靠猜。
- 动作：抓一条真实请求把每个入参代进复现脚本重算并与线上值比对，再换一条不同参数复算，两次都对才成立。
- 无效则：复算总差一位 → 查是否有本地未取到的服务端下发值（token/盐），去抓其下发点。
- 失效条件：签名依赖服务端私钥或一次性随机数时本地复算原理上不可能一致，只能 hook 取值。
